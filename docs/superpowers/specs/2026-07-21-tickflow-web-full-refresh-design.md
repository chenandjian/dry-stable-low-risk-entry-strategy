# TickFlow前端全市场强制重拉设计

## 1. 目标

在前端“K线数据”页面新增“TickFlow全市场重新拉取”按钮。点击后使用TickFlow批量接口为当前`stock_pool`全部股票强制重新获取历史日线并写入本地数据库，用于验证TickFlow全市场数据能力。

本功能是数据维护任务，不执行策略1至策略6，不生成候选股票，也不加入现有Tencent/Sina/Baidu回退链。

## 2. 固定参数

- 周期：`1d`
- 复权：`forward_additive`
- 每只股票历史：1100根
- 服务端处理分块：每块100只
- TickFlow SDK批量大小：100只
- SDK并发工作线程：5
- 批次失败重试：1次
- 更新模式：`backfill`，每次点击都强制整段重拉，不采用10根增量窗口

前端只展示参数，不允许临时修改，避免一次测试使用无法追溯的口径。

## 3. 页面设计

按钮放在`/data/kline-history`页面“全市场数据健康”标题区域，与“刷新健康状态”同级。

按钮文案：

- 空闲：`TickFlow全市场重新拉取`
- 运行中：`TickFlow重拉中...`

点击后必须二次确认，说明：

1. 将覆盖全部股票现有历史日线。
2. 数据固定使用`forward_additive`。
3. 写入前会备份SQLite数据库。
4. 任务可能运行较长时间，关闭页面不会停止后台任务。

页面展示独立状态卡：任务ID、状态、总股票数、已处理数、成功数、失败数、当前分块、开始时间、耗时、报告路径和错误摘要。运行期间每2秒轮询，页面刷新后继续读取后端实际状态。

## 4. 后端接口

### 4.1 启动

`POST /api/tickflow/full-refresh`

成功返回HTTP 202：

```json
{
  "task_id": "tickflow-web-20260721-200000-abcdef",
  "status": "running",
  "parameters": {
    "history_days": 1100,
    "chunk_size": 100,
    "batch_size": 100,
    "max_workers": 5,
    "adjustment": "forward_additive"
  }
}
```

以下情况返回HTTP 409：

- 已有TickFlow全市场任务运行。
- 任一策略扫描或回测正在运行。

### 4.2 状态

`GET /api/tickflow/full-refresh/status`

返回当前或最近一次任务状态。状态至少包括`idle/running/completed/completed_with_errors/failed`，并包含任务级进度和失败股票摘要。

## 5. 后台执行流程

1. 从当前配置解析数据库路径并初始化数据库。
2. 获取`stock_pool`快照；空股票池直接失败，不启动空任务。
3. 获取TickFlow专用互斥锁，并确认全局策略扫描/回测未运行。
4. 使用SQLite在线备份，备份文件写入`data/tickflow/backups/`。
5. 将股票按100只分块；每块调用现有`TickFlowDailyUpdateService`，模式固定为`backfill`，运行ID保持一致。
6. 每只股票验证成功后通过`replace_ohlc_with_metadata()`原子替换；失败股票保留原数据。
7. 每块完成后更新任务进度和JSON进度文件。
8. 全部完成后生成Markdown报告，释放锁并保留最终状态供前端查询。

全市场任务不得一次性在内存中保留全部股票的DataFrame。每个100只分块处理完成后释放该块响应，再进入下一块。

## 6. 失败与恢复

- 单只股票缺失、非法OHLC或历史缩短时标记失败，不修改其旧数据，不中断其他股票。
- TickFlow某一分块请求失败时，该块股票全部记录失败，继续后续分块。
- 后台线程未捕获异常时任务标记`failed`并记录错误，不得停留在`running`。
- 本期前端不提供“暂停”或“取消”，避免中断SQLite替换过程。
- 断点文件保留成功股票代码；服务重启后的自动恢复不在本期范围，但报告可用于后续仅重试失败股票。

## 7. 并发与一致性

- TickFlow任务使用独立线程和专用锁，同一时间只允许一个。
- 启动时与现有策略扫描/回测互斥。
- TickFlow运行期间后端拒绝新策略扫描，避免扫描读取到部分股票新数据、部分股票旧数据。
- 单只股票写入继续使用SQLite事务和整股原子替换。
- 前端状态只读取后端任务状态，不自行推算完成。

## 8. 修改范围

- `tickflow_data/service.py`：增加请求分块能力或可复用的分块执行入口。
- `tickflow_data/cli.py`：提取公共备份、进度和报告能力，供Web任务复用。
- `server.py`：增加TickFlow任务状态、启动/查询API和扫描互斥。
- `web/src/composables/useApi.js`：增加启动和状态接口。
- `web/src/pages/KlineHistory.vue`：增加按钮、确认和状态卡。
- 后端和前端测试文件：覆盖任务互斥、后台完成、部分失败、轮询恢复和按钮行为。

不修改策略1至策略6引擎、候选表和现有三源获取顺序。

## 9. 测试要求

### 后端

1. 启动全市场任务返回202并立即异步运行。
2. 参数固定为1100/100/100/5/`forward_additive`。
3. 超过100只时按分块调用，不一次加载全市场DataFrame。
4. 写库前创建备份。
5. 单股失败不覆盖旧数据，最终为`completed_with_errors`。
6. 重复启动、策略扫描运行和回测运行均返回409。
7. 未捕获异常最终标记`failed`并释放锁。
8. 状态接口返回真实进度和最终报告路径。

### 前端

1. 页面显示按钮和固定参数。
2. 点击确认后调用启动API。
3. 用户取消确认时不调用API。
4. 运行中按钮禁用并每2秒轮询。
5. 页面刷新后可恢复当前后台任务状态。
6. 完成时显示成功、失败和报告信息，并刷新K线健康状态。

## 10. 验收标准

1. 用户可以从前端启动TickFlow全市场1100根强制重拉。
2. 页面能持续看到真实任务进度，不会一闪而过。
3. 全市场按100只分块，内存不会累积全部DataFrame。
4. 写库前有备份，失败股票旧数据不丢失。
5. 任务与所有策略扫描/回测互斥。
6. 不影响现有三源链及六套策略。
7. 专项测试、后端完整回归、前端测试和构建全部通过。
