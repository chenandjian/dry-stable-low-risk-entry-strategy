# 行情数据获取模式设计

## 1. 目标

将 TickFlow 设为正式行情获取方式，同时完整保留 Tencent、AkShare-Sina、Baidu 传统多源链作为人工切换的备用模式。所有手动策略扫描、定时串行扫描、失败重试和中断恢复都必须服从当前配置，禁止 TickFlow 失败后自动回退传统源。

## 2. 配置与前端

在 `data` 下新增唯一模式字段：

```yaml
data:
  acquisition_mode: tickflow
  daily_sources:
    - tencent
    - sina
    - baidu
```

- `acquisition_mode` 只允许 `tickflow` 或 `legacy_multi_source`。
- 默认和正式配置使用 `tickflow`。
- `daily_sources` 继续保存传统模式的启用源和优先级；切换模式不得覆盖该列表。
- 策略配置页“日线数据获取模式”使用单选控件，保存后下一次任务生效。
- 切换必须由用户保存配置完成，运行时不允许自动切换。

## 3. 统一数据准备层

新增共享行情准备模块，位于扫描器与具体数据源之间，不包含任何策略判断。

### 3.1 TickFlow 模式

1. 根据最近完整交易日和元数据筛出确实需要更新的股票。
2. 使用 `TickFlowDailyUpdateService` 对这些股票执行批量 `update`，固定 `forward_additive`、每批100只、SDK并发5。
3. 已是当天有效缓存的股票不请求网络，供后续策略复用。
4. 批量成功的股票从本地 `daily_ohlc` 进入策略；失败股票返回明确的 TickFlow 失败结果并进入扫描失败列表。
5. 不调用 Tencent、AkShare-Sina 或 Baidu。
6. 策略1完成后，策略2至策略6再次进入准备层时应识别缓存已新鲜，不重复拉取。

### 3.2 传统多源模式

保持现有逐股 Tencent、AkShare-Sina、Baidu 获取、缓存新鲜度、停牌识别和失败重试语义。数据源顺序由 `daily_sources` 决定，不调用 TickFlow。

## 4. 指数数据

正式市场指数固定为：

| 本地代码 | TickFlow代码 | 名称 |
| --- | --- | --- |
| `sh000001` | `000001.SH` | 上证指数 |
| `sz399001` | `399001.SZ` | 深证成指 |
| `sz399006` | `399006.SZ` | 创业板指 |
| `hs300` / `sh000300` | `000300.SH` | 沪深300 |

- TickFlow 指数请求使用日线和不复权口径；股票继续固定 `forward_additive`。
- TickFlow 模式下，扫描使用本地 `market_index_ohlc` 中由 TickFlow 更新的数据，禁止临时请求新浪指数。
- 传统模式继续使用现有指数来源并写入相同规范表。
- 指数请求失败必须记录错误；要求真实指数的策略不得伪造或静默替代。

## 5. 扫描入口一致性

策略1至策略6扫描器都通过共享准备模块解析模式。服务端手动扫描、定时扫描、失败重试和中断恢复最终调用相同扫描器，因此不能各自复制模式判断。

每个扫描任务应保存或输出实际数据模式。运行中的任务使用启动时的配置快照，不因用户中途改配置而切换。

## 6. TickFlow全量维护任务

保留现有 `/api/tickflow/full-refresh` 和“K线数据”页按钮，其含义仍是显式执行 TickFlow 全量重拉：

1. 更新当前 `stock_pool` 的全部股票，固定1100根前复权日线。
2. 同一任务更新四个宽基指数，并写入 `market_index_ohlc`。
3. 写库前创建 SQLite 在线备份。
4. 股票或指数部分失败时保留成功数据、列出失败对象，任务为 `completed_with_errors`。
5. 本按钮是明确的 TickFlow 维护操作，不受 `acquisition_mode` 限制，也不会触发传统源。

## 7. 数据清理

代码和测试全部通过后，对当前 worktree 数据库先创建在线备份，再清空：

- `daily_ohlc`
- `daily_ohlc_metadata`
- `market_index_ohlc`

保留 `stock_pool`、任务、候选、回测、配置和策略4题材数据。清理后由用户手动点击 TickFlow 全量任务重建个股和宽基指数历史。

## 8. 错误与并发

- 不允许一个扫描任务混用两种模式。
- TickFlow 准备阶段与其他扫描继续使用现有全局互斥规则。
- TickFlow 缺少 SDK、认证失败、批量漏标的或非法 OHLC 时，相关股票必须失败，不得读取不新鲜缓存生成候选。
- 停牌股票在本次成功请求且目标日无交易时允许沿用上一有效交易日，并记录停牌/无交易状态。
- 全量任务和扫描均不得在内存中累计全市场 DataFrame。

## 9. 兼容性

- 不修改六套策略引擎、评分和候选旧字段。
- 保留 `daily_sources`、传统多源模块和现有 TickFlow API。
- 旧配置缺少 `acquisition_mode` 时按 `legacy_multi_source` 解析，避免升级后未经人工选择就改变旧部署行为；项目正式 `config.yaml` 显式写为 `tickflow`。

## 10. 验收标准

1. 前端可保存并恢复两种模式，且只有人工保存能切换。
2. TickFlow 模式的任一扫描不调用传统三源。
3. 传统模式不调用 TickFlow。
4. 定时任务、失败重试和恢复任务遵循启动配置。
5. 同日串行策略复用 TickFlow 缓存，不重复批量请求。
6. TickFlow 全量任务同时恢复股票与四个指数。
7. 清理后股票池仍存在，而两类行情表为空。
8. 专项、后端回归、前端测试和构建通过。
