# TickFlow数据新鲜度探测与扫描安全保护设计

## 1. 目标

修复TickFlow目标交易日数据尚未发布时，系统把全市场股票误判为停牌、最终产生零候选的问题；同时在前端“个股历史K线数据”页面增加一个只读的新鲜度测试面板，让用户直接核对TickFlow远端和本地数据库的最新日期。

本次不改变行情获取模式选择，不自动回退传统数据源，不修改策略1至策略6规则，也不让测试接口写入正式行情数据库。

## 2. 已确认故障

任务`s6-20260723-154238`的目标交易日为`2026-07-23`，但TickFlow返回的4995只股票最新日期均早于目标日，数据库没有任何`2026-07-23`个股K线，四个指数也全部缺失。现有`PreparedTickFlowSession.fetch()`仅凭`latest_date < target_trade_date`把每只股票标记为`suspended`，策略6随后追加`LATEST_TRADE_SUSPENDED`否决，导致正式候选和VCP确认候选同时为零。

此外，现有缓存新鲜度判断接受`latest_date <= target_date`。本次批量请求刷新了`fetched_at`但没有新增目标日K线，后续任务可能错误复用这份落后缓存而不再请求。

## 3. 正式扫描修复

### 3.1 缓存新鲜度

TickFlow普通股票缓存只有同时满足以下条件才算新鲜：

1. 元数据来源为`tickflow`。
2. `latest_date == target_trade_date`。
3. `fetched_at >= min_fetch_time`。

不得继续使用`latest_date <= target_trade_date`作为新鲜条件。已由任务上下文明确认定为停牌或无交易的股票仍沿用现有专用复用机制，不通过普通TickFlow缓存条件伪造。

### 3.2 全市场零覆盖保护

TickFlow批量更新结束后统计本次股票范围内目标交易日覆盖数：

- 若至少一只股票覆盖目标交易日：说明TickFlow已发布目标日行情。未覆盖目标日且请求成功的个股可继续按现有停牌/无交易语义处理。
- 若目标交易日覆盖数为0：判定为数据源级`TARGET_TRADE_DATE_UNAVAILABLE`，不得把全部股票解释为停牌。

零覆盖时，为本次待更新股票建立明确失败记录，错误信息至少包含目标日期和远端最新日期。扫描任务中的对应股票进入`failed`状态，保留在失败列表中供重新拉取；不得使用落后缓存产生候选。

该保护同样适用于只扫描部分股票的场景：若数据库中同一来源已经存在其他股票的目标日数据，可以证明TickFlow已发布目标日行情，此时单股缺失仍允许按个股停牌处理；否则按数据源目标日不可用处理。

### 3.3 指数

四个宽基指数继续要求精确覆盖目标交易日。缺少目标日时保存明确的指数失败结果和`MISSING/STALE`状态，不得提供空数据冒充最新市场环境。

## 4. TickFlow只读新鲜度探测

### 4.1 API

新增：

```text
POST /api/tickflow/freshness-check
```

请求：

```json
{
  "stock_code": "000655"
}
```

股票代码必须是6位数字。接口每次真实请求TickFlow：

1. 指定股票，使用正式股票前复权口径`forward_additive`。
2. 上证指数、深证成指、创业板指、沪深300，使用指数正式不复权口径。

接口为只读探测，不调用行情替换或元数据更新函数，不写`daily_ohlc`、`daily_ohlc_metadata`或`market_index_ohlc`。

### 4.2 返回结构

顶层返回：

- `checked_at`：实际探测时间。
- `target_trade_date`：按当前交易日规则计算的目标完整交易日。
- `overall_status`：`FRESH`、`STALE`、`PARTIAL_FAILURE`或`FAILED`。
- `stock`：指定股票探测结果。
- `indexes`：四个指数探测结果。

每个结果包含：

- `symbol`、`code`和中文名称。
- `remote_latest_date`：TickFlow本次响应最新日期。
- `local_latest_date`：当前本地数据库最新日期。
- `target_trade_date`。
- `row_count`。
- `elapsed_ms`。
- `status`：`FRESH`、`STALE`或`FAILED`。
- `error`：失败原因；成功时为空。

远端日期等于目标日期才是`FRESH`。早于目标日期为`STALE`，不得称为停牌。单项失败不阻断其他项目返回。

## 5. 前端

在`/data/kline-history`页面顶部现有TickFlow全量拉取区域旁新增“TickFlow数据新鲜度测试”面板：

1. 一个6位股票代码输入框。
2. 一个“测试远端新鲜度”按钮。
3. 请求期间按钮禁用并显示测试中。
4. 顶部展示目标完整交易日、检测时间和整体状态。
5. 表格展示指定股票和四个指数的远端最新日期、本地最新日期、状态、行数、耗时和错误。
6. 状态使用明确中文：最新、落后、请求失败。

测试面板不得触发全量重拉，不得修改当前分页查询条件，也不得影响已有TickFlow全量任务轮询。

## 6. 错误处理

- TickFlow SDK初始化失败：五个项目均返回失败，HTTP响应保持可解析，不返回半截HTML错误。
- 股票代码非法：HTTP 400，前端显示输入错误，不发起TickFlow请求。
- 股票请求失败但指数成功：整体为`PARTIAL_FAILURE`，保留指数结果。
- 指数请求失败但股票成功：同样为`PARTIAL_FAILURE`。
- TickFlow返回空表或缺少symbol：该项目为`FAILED`。
- TickFlow正常返回但日期落后：该项目为`STALE`，不是`FAILED`或`suspended`。

## 7. 测试

### 7.1 后端单元测试

1. 普通TickFlow缓存必须精确覆盖目标日才算新鲜。
2. 全批次目标日覆盖为0时，所有待更新股票返回数据源级失败，不标记停牌。
3. 部分股票覆盖目标日时，未覆盖个股仍可按个股无交易处理。
4. 多位股票代码、非法代码和空响应边界。
5. 新鲜度探测不调用任何数据库写函数。
6. 远端最新、落后和请求失败状态映射。
7. 四个指数和指定股票均被请求，单项失败不会丢失其他结果。

### 7.2 扫描集成测试

1. TickFlow全市场零覆盖时，策略6任务股票进入失败列表，候选数为0且失败原因明确。
2. 不再产生4995只`suspended`。
3. 目标日已发布时，正常停牌个股仍保持原有处理。
4. 策略1至策略5共享TickFlow准备路径不出现回归。

### 7.3 前端测试

1. 输入股票代码后调用新API。
2. 展示股票和四个指数共5行。
3. 展示目标日期、远端日期、本地日期及中文状态。
4. 请求中禁用按钮。
5. 非法输入和接口失败有明确提示。
6. 现有个股查询和全量重拉功能保持正常。

## 8. 兼容与交付

- 不修改现有TickFlow全量重拉API。
- 不修改数据获取模式配置和人工切换规则。
- 不修改策略评分、过滤和候选结构。
- 不自动回退腾讯、Sina或百度。
- 真实外部TickFlow验证只执行少量指定股票和四个指数，不执行额外全市场重拉。
- 形成真实验证报告，记录目标日、远端最新日、本地最新日和状态。
